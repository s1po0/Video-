# Clip size investigation

Through v15, the app re-encoded MP4 sections with x264 (`--force-keyframes-at-cuts` and `ultrafast`). This can produce a much higher bitrate and larger file than the input. Limiting the encoding bitrate reduces growth but cannot guarantee a file no larger than the source segment. The capped experiment was not released.

Version 16 uses FFmpeg stream copy, without `--force-keyframes-at-cuts`. It copies the source video and audio packets instead of recompressing. `tests/lossless-clip-integration.py` exercises yt-dlp with two separate H.264/AAC streams, B-frames, a long GOP, a non-keyframe start, bounded HTTP ranges, first displayed frames, and audio alignment in FFmpeg. In a local test of a 3–15 second cut, FFmpeg displayed the correct first frames, copied source packets, and aligned audio, but the output lasted 12.13 s rather than exactly 12 s. The test also shows the wrong first frames when an MP4 player ignores edit lists.

Stream copy is not a byte-for-byte size guarantee for the requested interval. MP4 can retain pre-roll packets from the previous keyframe, end packets for reordering, and container metadata. Actual size depends on the encoded source, keyframes, and mux overhead. Some players may display that pre-roll. The separate subtitle download currently rebases to the requested start; a player that displays pre-roll may therefore show subtitles out of sync.

Android playback is especially important: [FFmpegKitx PR 23](https://github.com/zqcformix/FFmpegKitx/pull/23) reports that its Media3 test and Xiaomi Gallery honored an MP4 edit list, but platform MediaPlayer on Android API 34 and 35 played from the earlier keyframe. The results are theirs, not a test of this app or the user's phone. [LosslessCut issue 3057](https://github.com/mifi/lossless-cut/issues/3057) explains how MP4 edit lists hide leading frames and notes player compatibility limits. Its observations are not a general guarantee for Android, audio, or all B-frame layouts.

Version 16 uses stream copy for MP4 clips. Playback and subtitle alignment still need verification on Android players the user actually uses. The supplied YouTube video is inaccessible from this build environment, so no real-site download or device benchmark has been performed.
