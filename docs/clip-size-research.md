# Clip size investigation

Through v15, the app re-encoded MP4 sections with x264 (`--force-keyframes-at-cuts` and `ultrafast`). This can produce a much higher bitrate and larger file than the input. Limiting the encoding bitrate reduces growth but cannot guarantee a file no larger than the source segment. The capped experiment was not released.

Version 16 uses FFmpeg stream copy, without `--force-keyframes-at-cuts`. It copies the source video and audio packets instead of recompressing. `tests/lossless-clip-integration.py` exercises yt-dlp with two separate H.264/AAC streams, B-frames, a long GOP, a non-keyframe start, bounded HTTP ranges, first displayed frames, and audio alignment in FFmpeg. In a local test of a 3–15 second cut, FFmpeg displayed the correct first frames, copied source packets, and aligned audio, but the output lasted 12.13 s rather than exactly 12 s. The test also shows the wrong first frames when an MP4 player ignores edit lists.

Stream copy is not a byte-for-byte size guarantee for the requested interval. MP4 can retain pre-roll packets from the previous keyframe, end packets for reordering, and container metadata. Actual size depends on the encoded source, keyframes, and mux overhead. Some players may display that pre-roll. The separate subtitle download currently rebases to the requested start; a player that displays pre-roll may therefore show subtitles out of sync.

Android playback is especially important: [FFmpegKitx PR 23](https://github.com/zqcformix/FFmpegKitx/pull/23) reports that its Media3 test and Xiaomi Gallery honored an MP4 edit list, but platform MediaPlayer on Android API 34 and 35 played from the earlier keyframe. The results are theirs, not a test of this app or the user's phone. [LosslessCut issue 3057](https://github.com/mifi/lossless-cut/issues/3057) explains how MP4 edit lists hide leading frames and notes player compatibility limits. Its observations are not a general guarantee for Android, audio, or all B-frame layouts.

Version 16 uses stream copy for MP4 clips. Playback and subtitle alignment still need verification on Android players the user actually uses. The supplied YouTube video is inaccessible from this build environment, so no real-site download or device benchmark has been performed.

## Version 17: reduce extra network data

FFmpeg's [HTTP protocol documentation](https://ffmpeg.org/ffmpeg-protocols.html) describes `request_size`, `initial_request_size`, and `short_seek_size`. Smaller initial requests can reduce data read while locating MP4 metadata; smaller regular requests reduce how much a forward seek reads through to keep a connection. Version 17 changes the fast MP4 clip path from 8 MiB to 2 MiB requests, uses 256 KiB for initial probing, keeps `short_seek_size` equal to the regular request size, and retains connection reuse. Fallback FFmpeg still uses its previous unbounded behavior.

A repeatable local test with separate H.264/AAC tracks, metadata at the end of the file, and a 3–15 second cut compared the same stream-copy output with both settings. The total lengths of ranges requested fell from 33,531,140 to 13,766,647 bytes, with byte-identical output. Requested range lengths are an upper bound, not measured data received: a client can close a response early, and TCP buffers, latency, server behavior, metadata position, and retries affect actual usage. This is one synthetic case, not evidence of savings or speed on YouTube. Smaller ranges can require more requests and may slow high-latency connections. The output bitrate and size are not reduced by these HTTP settings. A lower resolution can reduce the final size at a quality cost; the user chooses this, not the app.

Stream copy still retains necessary pre-roll and metadata, so it cannot promise that every output exactly equals the bytes corresponding to the selected time. The app stages the completed clip in its cache and copies it to MediaStore or a picked folder, so peak temporary disk space can approach two output copies during publication; this is not part of the APK. No real YouTube or Android-device test has been performed.

## Version 18: a short-track report

A user reported that version 17 showed the app's existing incomplete-file message. That message is produced when Android MediaExtractor reports an audio or video track substantially shorter than the requested MP4 clip. It does not establish why the track is short, whether the HTTP tuning caused it, or whether the reported duration accurately reflects playback on the user's device. No real YouTube/device reproduction is available here.

Version 18 validates the clip during the download attempt. If either track is reported too short, it discards that attempt and retries with version 16's 8 MiB settings. A second failure reports the track and measured/requested duration instead of the old generic message. It still checks for incomplete files and will not silently publish them. This retry can use additional data and is not a guarantee of success. Unit tests cover retry ordering, cleanup, errors, and duration thresholds; integration tests exercise both sets of HTTP arguments and compare their resulting clips, but do not replicate the user's Android failure.
